# Step 2: run one tick

## The core principle

> **Never wait for a full CI run before addressing review comments.** A comment fix pushes a new commit that re-triggers CI anyway, so handling comments *while CI is still running* collapses the two timelines instead of serializing them. Handle comments first; if that pass pushed, the old CI failure is against a dead SHA: skip it and let the new run start.
>
> **The same rule applies to an in-progress review.** Act on the feedback a reviewer has *already posted* rather than waiting for its 👀/"reviewing" signal to clear. The in-progress signal gates only the "looks ready" call (Step 3), never the work.

Read before the first tick; the ordering invariant here is the whole point of the skill.

## Bootstrap snapshot

A tick is fully resumable from disk, so any re-invocation drives it: a scheduler, `/loop`, or the user re-running the skill an hour later. Set `SKILL_DIR` to the directory containing this skill's SKILL.md, then take the first snapshot:

```bash
SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>";
STATE_DIR="${XDG_CACHE_HOME:-$HOME/.cache}/babysit-pr/<host>-<owner>-<repo>-<N>";
(umask 077; mkdir -p "$STATE_DIR") || exit 1;
PY="$(for c in python3 python py; do command -v "$c" >/dev/null 2>&1 && "$c" -c '' >/dev/null 2>&1 && { echo "$c"; break; }; done)"; [ -n "$PY" ] || { echo "no working Python 3 interpreter on PATH" >&2; exit 1; };
"$PY" "$SKILL_DIR/scripts/pr-snapshot" snapshot --pr <N> --repo <host>/<owner>/<repo> --state-dir "$STATE_DIR" --start-invocation --invocation-budget-seconds <seconds>
```

This is the only command that may start a budget. Use the user's requested duration when supplied; otherwise the fixed **8-hour default** (`28800`). The budget is spent in **active watch time**, not raw wall-clock: while the in-session watch runs, a span where the whole process was suspended (a closed laptop) is excluded from `invocation_elapsed_seconds`. Detection is coarse: an activity gap well above the poll interval is charged to dead time; ordinary polls, agent ticks, and human-blocked waits keep counting. A separate **3-day wall-clock backstop** caps every invocation. Checkpoint mode and the durable/cron path have no continuous poll cadence, so they keep wall-clock accounting.

Record the output's `invocation_id`, `invocation_started_at`, and `invocation_budget_seconds` as `RUN_INVOCATION_ID`, `RUN_STARTED_AT`, and `RUN_BUDGET_SECONDS`. Require `invocation_elapsed_seconds <= 60`; otherwise fail before arming a watcher. Durable PR dispositions, dedup, and trajectory survive a new invocation, but its budget clock does not. Every later snapshot, mark, and watch arm must pass all three values (`--invocation-id "$RUN_INVOCATION_ID" --session-started-at "$RUN_STARTED_AT" --invocation-budget-seconds "$RUN_BUDGET_SECONDS"`); the helper rejects a missing or mismatched token, anchor, or budget. Never use `--start-invocation` after this first snapshot: re-arms, mutations, retries, and review/CI rounds share one non-rolling budget.

**`<host>` in `STATE_DIR` and `--repo` is load-bearing for GitHub Enterprise.** Derive it from the PR URL's host (`github.com` on the public host) and use the same value in every command. Keying only by `<owner>-<repo>-<N>` would let two PRs with the same `owner/repo#N` on different hosts share one `state.json`. Passing the host in `--repo <host>/<owner>/<repo>` makes the helper's first `gh pr view` query the right host.

**Shell state does not persist between separate tool calls.** Re-set `SKILL_DIR`, `STATE_DIR`, `PY`, and the three `RUN_*` values inline in every command below, or pass absolute values directly. A bare `$SKILL_DIR` in a fresh call is empty.

Treat every fresh `snapshot` as the canonical source of truth for review-thread state; its fetch paginates the full thread connection. Never replace it with a one-shot `reviewThreads(first:N)` result. If a direct diagnostic query is genuinely necessary, follow `pageInfo` until `hasNextPage == false` before drawing a count conclusion.

## Arm the change detector

**In the self-sustaining watch, back the tick with the background change detector.** `pr-snapshot watch` runs the same fetch and diff on an interval with **no agent tokens** and prints a single `BABYSIT_WAKE {reason,url,...}` line *only* when there is work to inspect (`actionable` for an unresolved thread or failed CI; `feedback-candidate` for a non-thread body that still needs resolver judgment; `branch-currency`) or a stop/residual condition (`terminal` / `blocked-external` / `blocked-external-drained` / `blocked-failing` / `base-ref-blocked` / `chain-blocked` / `unrequested-base-merge` / `needs-human` / `merge-ready` after the settle window / `review-evidence-moved` / `max-runtime` / `stop-signal` / `invocation-superseded`), then exits. A `feedback-candidate` wake does not claim a fix is required: a resolver pass that silently drops the body is a normal outcome. Run it in the background with the host's tools (Step 1) and, on the sentinel, run the tick below:

```bash
SKILL_DIR="<absolute path of this skill's directory>"; STATE_DIR="${XDG_CACHE_HOME:-$HOME/.cache}/babysit-pr/<host>-<owner>-<repo>-<N>"; RUN_INVOCATION_ID="<invocation_id>"; RUN_STARTED_AT="<invocation_started_at>"; RUN_BUDGET_SECONDS="<invocation_budget_seconds>";
PY="$(for c in python3 python py; do command -v "$c" >/dev/null 2>&1 && "$c" -c '' >/dev/null 2>&1 && { echo "$c"; break; }; done)"; [ -n "$PY" ] || { echo "no working Python 3 interpreter on PATH" >&2; exit 1; };
"$PY" "$SKILL_DIR/scripts/pr-snapshot" watch --pr <N> --repo <host>/<owner>/<repo> --state-dir "$STATE_DIR" --interval 150 --invocation-id "$RUN_INVOCATION_ID" --session-started-at "$RUN_STARTED_AT" --invocation-budget-seconds "$RUN_BUDGET_SECONDS"
```

Watch ownership is **latest-valid-watcher-wins**. A newer invocation first cancels any older invocation still preflighting, but does not disturb the active watcher; only after a successful first snapshot does it supersede and terminate that process. Every wake and snapshot carries `watch_generation`. On delivery, compare the wake's generation with one fresh snapshot: a stale wake is discarded and coalesced into that read, and a current wake whose attention set already cleared is a no-op. An `invocation-superseded` wake means another explicit invocation owns the state: end the old loop without acting or re-arming. Re-arming with the same invocation token preserves `last_change_at`, the start anchor, and the budget.

Do **not** pass `--settle-seconds` or `--blocked-external-drain-seconds` on the ordinary arm. The 300s default is the initial merge-ready settle window; Step 3 alone widens it.

## What the snapshot emits

The **attention set**: unresolved threads you have not acted on, **non-thread feedback candidates** (top-level PR comments and review bodies) you have not classified, and failing checks on the current head you have not dispatched, plus the exact current `branch_currency` item and its `attention` route. Also `pr_state`, `pr_is_draft`, `mergeable`, `merge_state_status`, `mergeability_certain`, `base`, `base_ref_blocker`, `host_branch_update_capability`, `branch_currency_blocker`, `chain_blocker`, `review_decision`, `head_sha`, `quiet_seconds`, `invocation_elapsed_seconds`, `invocation_remaining_seconds`, `persisted_state_age_seconds`, `checks_awaiting_approval` / `blocked_external` with the head-scoped `blocked_external_*` review-drain facts (Step 3), a `pr_chain` block, and a `trajectory` block (cross-tick facts: `check_recur_max`, `recurring_checks`, `unresolved_trend`, `new_threads_this_tick`, `stream_alternations`, `heads_since_progress`, `invariant_rounds`).

`base.historical_oid` is GitHub's historical `baseRefOid` and is diagnostic only. Current-base identity requires the exact Git ref (`base.oid`) to match the PR's `baseRef.target.oid` (`base.graphql_oid`), and for a mergeable result the generated merge commit must name that base and the observed head as its parents. Only that proven binding emits `base.identity == "current"`; base movement emits `race`, a pending merge computation `mergeability-pending`, a failed probe `probe-error`. These disable `mergeability_certain` and re-poll. Invocation time and persisted-state age are separate; never report one as the other.

The field is named `actionable.comments`, but its members are candidates awaiting classification, not proven action items. The fetch excludes only empty bodies, including from the PR author, since an author asking for a change on their agent-opened PR is ordinary feedback; loop prevention is the `dispatched` mark, not identity. The snapshot **never** marks an item handled just from observing it: it stays in the set until you `mark` it or remote truth removes it. Every `mark` must present the run's three invocation values, so a stale tick fails before it can silence work in a newer invocation. The state schema and claim-act-confirm protocol are in `references/watch-loop.md`.

**The `trajectory` is facts, not a verdict; the leaf judges convergence.** When it crosses a trigger (`check_recur_max >= 2`, `stream_alternations >= 3`, a rising `unresolved_trend` with `new_threads_this_tick > 0` across passes, `heads_since_progress >= 2`, or any `invariant_rounds[].rounds >= 2`), pass it to that tick's CI pass or `resolve-pr-feedback` call as **mandatory input** before anything mutates, and let that pass decide whether this is ordinary progress or non-convergence. Never declare non-convergence yourself. Protocol: `references/watch-loop.md` § Non-convergence.

## The ordering invariant

1. **Terminal check first.** If `pr_state` is `MERGED` or `CLOSED`, stop and report.
2. **Capture the head SHA** (the snapshot's `head_sha`) so you can tell later whether the comment pass pushed.
3. **Feedback before CI.** If the attention set has unresolved threads **or** non-thread candidates (`counts.threads > 0` or `counts.comments > 0`), invoke `resolve-pr-feedback` **once** with the PR's base `[HOST/]OWNER/REPO#N` or full URL from the snapshot's `url` (so a fork PR resolves against the upstream base, not the fork's `origin`), with `mode:pipeline` and the scope from "Bounded authority" below. It re-fetches and judges all feedback, parks `needs-human` items and returns them as structured residuals instead of asking, and is idempotent on empty. When a review trigger above is crossed, pass the `trajectory`; when the recurring items are *valid* and share one root, also request a **bounded-class assessment** so it fixes the equivalent sites in one pass. An `invariant_rounds[].rounds >= 2` trigger routes the trajectory **before** this pass may push. One resolve pass per tick.

   Its result names what it fixed (each root with the items it covered and a stable `invariant_key`), what it returned as `needs-human`, and what it silently dropped. Record all of it so the loop stops re-dispatching: each thread the pass handled gets `--disposition dispatched` (with `--invariant-key` when its root returned one); **every comment you passed** gets `--disposition dispatched` unless a `needs-human` object covers it. A top-level comment never drops out of the fetch on its own, so marking only the ones it *handled* would leave silently dropped candidates in the set forever and the loop would never settle. Each returned `needs-human` object is written to a JSON file and parked with one residual mark, which freezes all of its sources under one decision (`references/watch-loop.md` § Recording residuals).

   ```bash
   SKILL_DIR="<absolute path of this skill's directory>"; STATE_DIR="${XDG_CACHE_HOME:-$HOME/.cache}/babysit-pr/<host>-<owner>-<repo>-<N>";
   python3 "$SKILL_DIR/scripts/pr-snapshot" mark --pr <N> --repo <host>/<owner>/<repo> --state-dir "$STATE_DIR" --invocation-id "<invocation_id>" --session-started-at "<invocation_started_at>" --invocation-budget-seconds "<invocation_budget_seconds>" --thread <ID> --disposition dispatched --invariant-key <key-from-the-resolver>
   ```

   Later examples show only the flags that differ; every `mark` keeps the same `--state-dir` and three invocation flags, written out in full (do not pack them into one shell variable: zsh does not word-split it).

   - Comment handled or dropped: `mark ... --comment <ID> --disposition dispatched`
   - Needs-human object: `mark --pr <N> --repo <host>/<owner>/<repo> ... --disposition needs-human --residual-file "$STATE_DIR/residual-<n>.json"`

   Passing `--pr`/`--repo` on a **thread** mark is load-bearing: `mark` re-reads the thread's current last comment as the reactivation baseline, so a reviewer reply that lands before the next snapshot re-opens the thread instead of being swallowed. A **dispatched comment** stays silenced until an explicit `--disposition open`; it is never reactivated by a body edit, because status bots (changeset-bot, CodeRabbit, Codecov) rewrite their bodies on every push. A parked comment does reactivate when its body is edited, since a human may answer by editing; a residual mark that covers one comment can pass `--comment <ID> --acted-edit-id <edit_id from this tick's actionable.comments>` to pin that baseline. On a fix outcome, persist the resolver-returned `invariant_key` on that dispatched mark; omit the flag when it returned none, and never pass it on a `needs-human` mark. The script counts each key per unique head and never infers one.

   Retain the resolver's **non-routine verdicts** (`fixed-differently`, `declined`, `not-addressing`) for the Step 4 summary; a plain `fixed` is routine.
4. **Stale-SHA cancellation.** Compare the current head SHA with step 2's. If it **changed**, the CI failures in this snapshot are against a dead SHA: do not act on them; the new run surfaces next tick. Otherwise continue.
5. **CI on the current head.** Aggregate *all* actionable failing checks into one remediation pass, never one per check, following `references/ci-failures.md`. When a CI trigger above is crossed, carry the `trajectory` (`recurring_checks`, `check_recur_max`, `heads_since_progress`) into that pass. Then record each check you acted on with `mark ... --check "<key>"` so it is not re-dispatched at this head (a new head SHA clears these automatically). A CI `needs-human` is parked with a residual file whose source kind is `check`.
6. **Branch currency (the third stream, after comments and CI).** Consume the exact current `branch_currency` item; never infer one from merge-state prose. `UNKNOWN` mergeability or any non-null `base_ref_blocker` or `chain_blocker` yields no item and is only re-polled. Only a PR whose base is the repo's default branch and whose parent PRs (if any) are closed or merged gets an item (route `normal-base`); an open child PR does not disqualify it, but this route never mutates the child.
   - **Inspection and claim.** If `attention == "inspect"`, first preview the current conflict and compute its semantic conflict fingerprint (sorted conflicted paths plus their stage blob identities, excluding the base OID). Compare it with `parked_semantic_fingerprints`, then mark `--currency-key <key> --currency-inspected-fingerprint <fingerprint>`. Unchanged evidence stays parked (that mark then also takes a `currency` residual file for the new key); changed evidence reopens the item. For `attention == "claim"`, and only while budget remains, mark the exact item **before any external mutation or local merge**: `mark ... --currency-key <currency_key> --currency-disposition claimed`.
   - **Re-entry into `claimed` is reconciliation only:** inspect remote and local evidence, never resubmit. Record exactly one of `--currency-outcome mutation-observed|proven-no-mutation|ambiguous`. One retry is possible only after conclusive no-mutation proof and the engine's backoff; an ambiguous result never retries and needs a residual file on that same mark. Confirm with `--currency-key <key> --currency-disposition confirmed`, or park with a residual mark whose source kind is `currency` and whose id is the currency key.
   - **`BEHIND`: host-owned update only.** Proceed only with `host_branch_update_capability == true`; `false` or `unknown` is a `needs-human` path. After the claim, revalidate that remote head and base OIDs still equal the observation, then call `PUT /repos/{owner}/{repo}/pulls/{number}/update-branch` once with `expected_head_sha` set to the claimed head. An HTTP 422 head mismatch is a stale claim: re-snapshot and reconcile without resubmitting. Host acceptance is `mutation-observed`, not completion; confirm only after a fresh snapshot and ancestry evidence prove the new head contains the observed base OID.
   - **`DIRTY`: exact-base local repair only.** Prove, without mutating, push authority to the exact head ref; unknown or denied authority is `needs-human`. Require a clean PR-head checkout at the observed head, fetch the exact observed base OID, and run a non-mutating merge preview. A resolution is mechanical only with **positive intent evidence** and **no reasonable alternative behavior**. Two plausible resolutions, a behavior or intent choice, unbounded scope, stale OIDs, or missing authority means abort safely and park with a `currency` residual mark plus `--semantic-conflict-fingerprint <fingerprint>`, its `decision_context` carrying concise options, tradeoffs, and a lean.
   - **Apply a mechanical `DIRTY` repair:** claim and revalidate again, merge that exact base OID, and mark `--currency-outcome mutation-observed` as soon as the local merge starts. Resolve only the previewed conflict, validate proportionally, and push normally. **Never rebase or force-push.** Reconcile or abort an interrupted merge before parking; never layer a second attempt over it. Confirm only when the remote head equals or contains the validated merge commit and a fresh snapshot clears the gate. Remote head movement alone is not proof.
7. **After any mutation, re-snapshot** at the start of the next tick with the same three invocation values. Do not run a second `snapshot` mid-tick to re-derive CI; that causes stale-SHA confusion.
8. **CodeRabbit on the head, last.** When CodeRabbit is active on the PR, read `references/coderabbit.md` and run its helper after this tick's work: `--wait 180` on the first tick or when this tick pushed (with a shell timeout of at least 240 seconds), `--wait 0` otherwise. Its `state` feeds Step 3.

**Before any write** (rerun, push, reply), the delegated work re-validates against remote, but a local state lock does not stop a second babysitter or a human from acting, so never assume the snapshot is still current at mutation time. `resolve-pr-feedback` owns its own commit, push, reply, and resolve; this skill orchestrates, records, and reports.

## Pre-authorization and bounded authority

**Running the babysitter pre-authorizes its mutations.** The loop commits, pushes, and resolves review threads (replying under `full` or on a CodeRabbit-only thread) as its normal operation; never pause to ask the user to approve them. A general "confirm before pushing" habit governs your own ad-hoc actions, not the loop's owned mutations. The only things the loop hands to the user are the **merge** decision, a **`needs-human`** residual it deliberately did not decide, the **blocked-external** handback (Step 3), and a possibly stale PR description (Step 4).

**The authority you pass down is bounded.** Scope carried to `resolve-pr-feedback` and to the CI pass: **target** = this PR's head; **actions** = fix / commit / push / resolve, plus reply when the voice allows it (`full`, or a CodeRabbit-only thread); **exclusions** = merge, rebase, force-push, approve CI, review dismissal, PR-description edits, and, when quiet, replying outside the CodeRabbit-only carve-out; **attribution** = the `pr.attribution` value; **origin** = the user's babysit invocation. A delegate may narrow this but never broaden it. Hosts do not reliably carry a scope in-band, so you enforce the exclusions when composing results: reject and re-surface any result that performed an excluded action.

**Pre-authorization is not deafness.** A live user instruction during the run ("stop pushing", "leave CI alone", "stop commenting", which drops the run to quiet, or "go ahead and comment", which raises it to `full`) immediately narrows, redirects, or revokes the envelope. Re-evaluate the remaining work against it before the next mutation.
